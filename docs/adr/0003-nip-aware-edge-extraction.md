# ADR-0003: エッジ抽出をNIP準拠の単一モジュールに統一する

- ステータス: 採用
- 日付: 2026-06-10

## コンテキスト

旧実装は「イベントの全pタグ＝インタラクション」と解釈し、クラスタリングと3D可視化が別々のエッジ構築コードを持っていた。この解釈はNostrの仕様と食い違う: NIP-10はリプライのpタグにスレッド先祖全員を複製し（実測でpタグ付きノートの22〜29%が複数pタグ、最大8個）、NIP-25はリアクションに対象ノートのタグをコピーする。どちらも「会話していない相手」へのエッジを量産する。zap（NIP-57、実コストを伴う最強の関与シグナル）は未使用だった。

## 決定

エッジ抽出を`interaction-edges.ts`に一本化し、クラスタリング（`buildInteractionGraph`）と可視化（`buildGraph`)の両方が同じ定義を使う。各NIPの仕様通りに解釈する:

| イベント | 解釈 | エッジ型 |
|---|---|---|
| kind 1 | `reply`マーカー付きeタグ（位置的fallback: 最後のeタグ）が返信先。先祖・メンションは格下げ | `reply` / `mention` |
| kind 1 `q`タグ | NIP-18引用 | `quote` |
| kind 7 | NIP-25: 最後のpタグのみが対象著者 | `reaction` |
| kind 9735 | NIP-57: 受領者=`p`、送信者=`P`またはdescription内zap requestのpubkey | `zap` |

eタグ/qタグの著者解決はタグ内pubkeyヒント→ロード済みイベントのid→著者インデックスの順で行い、pタグの無いリプライもエッジ化する。アプリはkind 9735をグローバル窓・ライブ購読・表示ユーザ向け`#p`クエリで取得する。

## 結果

- 品質を維持したまま（Q 0.803 vs 0.816）接続ユーザとエッジが増えた（+4ノード/+5エッジ、zap単独で16ノード）。データセット2つで確認済み
- 可視化とクラスタリングの「インタラクション」の定義が一致し、見た目と分析が矛盾しない
- エッジ型が7種（reply/mention/quote/repost/reaction/zap/follow）に増え、重み設定の自由度が上がった。重み比への感度は低いことを実測済み（Q変動0.79〜0.81）
